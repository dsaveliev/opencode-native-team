## Существенное

### C-1. Правило «полного раздела» охраняется наличием одного ключа

`scripts/validate.py`, шаг `[5]`:

```python
if "*" not in rev:
    err("... reviewer bash map must be COMPLETE (catch-all '*' required ...)")
```

Проверяется присутствие catch-all. Не проверяется, что map действительно полный.
Подставил в пример-конфиг:

```json
"permission": { "bash": { "*": "deny", "go test ./...": "allow" } }
```

Результат:

```
[5] examples/opencode.json.example
  ok   example config: complete reviewer map, no global allow, model routing
ALL CHECKS PASSED
```

Этот конфиг имеет catch-all и тест-команду, то есть проходит обе проверки,
но при этом:

- **ревьюер теряет `git diff*`, `git log*`, `git show*`, `git status*`** —
  то есть не может прочитать диф, а это его основная функция;
- **исчезают все семь deny-правил на разделители** — та самая митигация
  инъекций, которую README описывает как действующую.

И это тот самый файл, который пользователю прямо предписано править:
`install.sh` печатает «customize models and test commands for your language».
Самая вероятная правка — сократить map до нужного — тихо снимает защиту,
а валидатор подтверждает «complete reviewer map».

**Фикс (это и есть настоящее правило):** map в JSON обязан быть надмножеством
`bash` из `agents/reviewer.md` — те же ключи с теми же значениями, плюс
языковые добавки, и catch-all первым. Валидатор уже парсит frontmatter
на шаге `[2]`, так что сравнение — около десяти строк:

```python
fm_bash = fm["reviewer"]["permission"]["bash"]
missing = {k: v for k, v in fm_bash.items() if rev.get(k) != v}
if missing:
    err(f"opencode.json.example: reviewer bash map must be a superset of the "
        f"contract's; missing/changed: {sorted(missing)}")
```

### C-2. Отгружаемый конфиг не поддерживает заявленный основной сценарий, а валидатор запрещает это починить

Новый раздел README:

> **Autonomous (headless) runs** additionally need a top-level
> `"permission": {"bash": {"*": "allow"}}` in the project config, or every
> command falls back to your global default (`ask` = auto-reject headless).

При этом:

- `examples/opencode.json.example` такого блока **не содержит**;
- `install.sh` копирует этот файл в проект как `.opencode/opencode.json`;
- `validate.py` шаг `[5]` **ошибается**, если блок появится:
  `err("opencode.json.example: global bash wildcard allow (R-5 regression)")`.

Итог: из коробки автономный прогон — то, что README называет основным режимом
(«The team then runs autonomously») — не работает; каждый пользователь обязан
править конфиг вручную; а CI не даст положить правку в пример.

**Здесь нужно признать, что моё замечание R-5 устарело.** Оно было гипотезой
о неизвестном порядке слияния: «если глобальный `"*": "allow"` окажется после
агентского `"*": "deny"`, блеклист аннулируется». Вы это измерили —
«agent frontmatter denies take precedence over top-level allows (probed)» —
и гипотеза не подтвердилась. Значит охранять нужно обратное.

**Фикс:** добавить top-level блок в пример, а шаг `[5]` развернуть:
ошибка, если top-level `permission.bash["*"]` **отсутствует** (headless
не поедет), с комментарием, что это безопасно по результатам пробы.
Текущая проверка охраняет опровергнутую гипотезу против подтверждённого факта.

### C-3. Дублирование из 17 правил не защищено от расхождения

Оборотная сторона C-1. Теперь `bash`-карта ревьюера живёт в двух местах:
`agents/reviewer.md` (контракт) и `examples/opencode.json.example` (который
побеждает для любого проекта, где он установлен). Семнадцать правил продублированы,
дрейф не проверяется ничем.

Сценарий: кто-то добавляет в контракт новое deny-правило (как `*\n*` в v5.1.3) —
в JSON оно не попадает, а JSON для установленных проектов главнее. Защита
ухудшается молча, и тот самый класс «заявлено в контракте, фактически
не действует» возвращается через новую дверь.

Проверка-надмножество из C-1 закрывает и это: она двусторонняя по смыслу —
любое правило контракта обязано присутствовать в JSON.

Отдельно стоит зафиксировать честную цену решения об агностичности.
В раунде 2 я оценил его как «~40 минут, новых сущностей ноль». После пробы
видно, что реальная цена — дублирование всей карты прав в каждом проекте.
Решение всё равно разумное (альтернативы хуже), но оценку стоит поправить
в `docs/`, чтобы она не осталась ещё одним прогнозом, поданным как факт.

### C-5. Шаг `[9]` зашит на русский формат заголовка

```python
subj_re = re.compile("[Кк]оммит(?:ы)?\\s+`?([0-9a-f]{7,40})")
```

То есть каждый `docs/review-*.md` обязан содержать «Коммит/коммиты `<sha>`»
в первых 400 символах. Ревью, написанное по-английски («Commit `abc1234`»),
провалит проверку с сообщением «no subject commit line (in Cyrillic)».

Для репозитория, где решение §7 — английский для публикации, механическая
проверка теперь зависит от русской прозы. Комментарий в исходнике сам отмечает
неловкость (экранирование ради ASCII-чистоты файла).

**Фикс:** принимать оба варианта — `(?:[Кк]оммит(?:ы)?|Commit)`.
