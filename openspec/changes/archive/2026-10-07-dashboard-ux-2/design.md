# Design

## Context

See proposal.md - Why. The dashboard is generated by
`scripts/gen-team-dashboard.py` (data collection + HTML render + embedded
poller JS) and served by `scripts/dashboard_server.py` (`GET /`, `GET /state`).
The server is a thin transport around the generator's output; every change
here lands in the generator (data + render + page JS). The stage stepper,
agents table, activity chart, task tree, work log, and summary tiles all
render from `collect_data()` output. Constraint: the read-only observation
guarantee (spec: no writes into the observed project beyond the sanctioned
final snapshot) rules out server-side log accumulation.

## Goals / Non-Goals

**Goals:**
- Stage indicator that matches wave-based runs and never moves backward.
- Presentation fixes that make a live run readable at a glance (ordering,
  task tree, active highlight, ETA projection, anchors, panels).
- Repaint-safe interactivity (expansion preserved) and reload-safe work log
  history (client buffer).

**Non-Goals:**
- Control plane (POST stays 405-reserved).
- Estimates stored in tasks.md or any change to /team, /team-change, or
  apply-state formats.
- Server-side persistence of work-log history (rejected: extra writes into
  the observed project).

## Decisions

### D1: Macro stage from task progress + secondary activity label

Macro stage mapping: no tasks checked -> plan; unchecked tasks remain ->
code; all tasks checked and an orchestrator/reviewer session still active ->
review; change archived (no active session) -> done. The current-activity
label ("now: coder, wave 3") keeps today's freshest-subagent-role signal
(10-minute horizon) with a wave counter: wave number = count of coder
sessions created after the first reviewer session. Alternative rejected:
monotonic ratchet over the old role-based stage (would lie during wave B
coding, showing "review").

### D2: Ordering by first activity

Both the agents table rows and the activity chart lanes sort by
`min(created)` of the agent's sessions inside the window. Replaces
`sorted(agents.items())` (alphabetical).

### D3: Repaint preserves expansion via keyed re-open

The poller keeps full-container replacement (simple, signature-driven) and
gains a pre-repaint snapshot of open `<details>` keys, reapplied after
replacement. Keys are stable and derived per panel: work log entry =
`agent + part timestamp`; commit = sha; task = change name + top-level
title. Alternative rejected: per-row DOM diffing (a custom vdom for a
status page - over-engineering).

### D4: Work log history in localStorage

Key: `dash-log:<directory-hash>:<window-start-ms>`. Before each apply,
entries from `/state` merge into the buffer (newest wins by timestamp, cap
~500). Render = buffer, newest first. Buffer is dropped when
`window-start-ms` changes. No server writes. Alternative rejected:
`tmp/*.jsonl` accumulation file (violates the "no extra writes" reading of
the observation guarantee the user chose).

### D5: Tool errors as a sibling panel

`load_parts` already counts errored parts (`state.status == "error"`); it
additionally emits the last ~30 error entries (tool, session -> agent,
time, first ~120 chars of `state.input` serialized). Layout: Work Log |
Tool Errors on one row, mirroring Tasks | Commits.

### D6: ETA projection from completed top-level tasks

Duration of a completed top-level task = span of the wave sessions whose
titles reference that task id (wave start = coder session creation, end =
last activity of the wave's reviewer session), falling back to the whole
run span when no title references resolve. Projection = median of completed
durations; rendered with an explicit "~" prefix and a muted style. No
projection until the first top-level completion. Alternatives rejected:
parsing checkbox-flip times from git history (heavier, brittle for runs
that do not commit task flips); estimates in tasks.md (schema change,
out of scope by decision).

### D7: Task tree restructure

Top-level tasks become `<details>` rows (checkbox state + title + elapsed
+ optional "~eta" in the summary line; subtasks inside). Highlight: task
ids parsed from the active subagent session's title (existing pattern
"Wave C: tasks 2.1 + 2.2") mark the in-work rows. Styling: muted palette,
thin indentation guides, softer counters - CSS only.

### D8: Summary tiles as anchors

Tiles wrap in `<a href="#panel-tasks|#panel-commits|#panel-agents">` with
matching ids on panels; spawns tile anchors to agents. No JS needed.

## Risks / Trade-offs

- Title-based task-id parsing (D6/D7) depends on the wave-naming convention
  of /team and /team-change prompts; a renamed convention degrades to
  "no highlight / whole-run fallback", never to wrong hard data.
- localStorage buffer is per-browser; a different machine or a cleared
  browser loses pre-reload history (accepted: zero server writes wins).
- Median projection is crude for heterogeneous tasks; it is labeled as an
  estimate everywhere it appears.
